# Тестирование конкурентного кода

## go test -race — ваш первый и главный помощник

```sh
# Запустить только один тест с детектором гонок
go test -race -run TestMyFunction ./mypackage

# Запустить все тесты в проекте с детектором гонок
go test -race ./...
```

go test -race — это не отдельный тест, а флаг, который включает детектор гонок данных во время выполнения ваших тестов. Он не найдет логические ошибки (например, дедлок), но безжалостно выловит ситуации, когда несколько горутин обращаются к одной памяти без синхронизации.

## Тесты с таймаутом/контекстом, чтобы избежать зависаний

Проблема: Ваш тест может зависнуть. Например, вы тестируете функцию, которая должна отправить данные в канал. Если в функции есть баг и она никогда этого не делает, ваш тест будет вечно ждать на result := <-ch и заблокирует весь тестовый набор.

Решение: Всегда ограничивайте время ожидания в тестах. Лучший способ для этого — context.WithTimeout.

Код: Тест, который не зависнет
Этот пример показывает, как написать надежный тест, который не будет зависать бесконечно, если тестируемая функция имеет баг. Предположим, мы тестируем функцию doWork, которая должна вернуть результат через канал.

```go
// worker.go
package mypackage

import "time"

func doWork(done chan<- string) {
    time.Sleep(100 * time.Millisecond)
    done <- "work complete"
}
```

Теперь напишем надежный тест для нее.

```go
// worker_test.go
package mypackage

import (
    "context"
    "testing"
    "time"
)

func TestDoWork(t *testing.T) {
    // Создаем контекст с таймаутом в 1 секунду.
    // Если doWork не завершится за это время, тест провалится.
    ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
    defer cancel()

    // Буфер на 1: если тест завершится по таймауту, doWork все равно
    // сможет положить результат и завершиться — горутина не утечет
    resultCh := make(chan string, 1)

    // Запускаем тестируемую функцию
    go doWork(resultCh)

    // Используем select, чтобы ждать либо результат, либо таймаут
    select {
    case result := <-resultCh:
        // Результат получен вовремя
        if result != "work complete" {
            t.Errorf("Неверный результат: %s", result)
        }
    case <-ctx.Done():
        // Контекст был отменен по таймауту
        t.Fatal("Тест не завершился за отведенное время (таймаут)")
    }
}
```

### Антипаттерн: "Fire-and-Forget" Горутины

- Как выглядит: go doSomething() без какого-либо способа контролировать ее или узнать, когда она завершилась.
- Проблема: Если doSomething зависнет (например, в ожидании из канала), эта горутина будет "жить" вечно, потребляя память. Это утечка горутины.
- Как исправить: Всегда думайте о жизненном цикле. Если вы запускаете горутину, вы должны нести ответственность за ее остановку. Передавайте ей context или возвращайте из функции done канал / cancelFunc.

### Антипаттерн: Закрытие канала получателем

- Как выглядит: Горутина, которая только читает из канала, решает его закрыть.
- Проблема: Если отправитель попытается отправить данные в уже закрытый канал, произойдет паника.
- Как исправить: "Кто пишет, тот и закрывает". Только та горутина, которая отправляет данные и знает, что их больше не будет, должна закрывать канал.

### Антипаттерн: Использование глобальных переменных для синхронизации

- Как выглядит: var globalCounter int и несколько горутин, которые его увеличивают без мьютекса.
- Проблема: Это прямой путь к гонке данных. Такой код очень сложно отлаживать и понимать.
- Как исправить: Предпочитайте передачу данных через каналы. Если все же нужно разделять память, инкапсулируйте ее в структуру вместе с мьютексом.

### Антипаттерн: Забытый defer mutex.Unlock()

- Как выглядит:

```go
m.Lock()
if someCondition {
    return // Упс! Unlock() никогда не вызовется
}
m.Unlock()
```

- Проблема: Если между Lock() и Unlock() происходит return или panic, мьютекс останется заблокированным навсегда. Это дедлок для всех остальных горутин.
- Как исправить: Всегда используйте идиому defer m.Unlock() сразу после m.Lock(). Это железное правило.

### Антипаттерн: Неправильное использование default в select

- Как выглядит: "Спин-луп" в цикле с select и default.

```go
for {
    select {
    case <-ch:
        // обработка
    default:
        // ничего не делаем
    }
}
```

- Проблема: Если канал ch не готов, default сработает немедленно, и цикл начнется заново. Это приведет к 100% загрузке ядра на пустую работу ("busy waiting").
- Как исправить: Если вам нужно неблокирующее поведение, используйте default осмысленно (например, для попытки отправки). Если же вам нужно ждать, уберите default и позвольте select заблокироваться.

### Итог: Золотые правила тестирования конкурентного кода

Всегда запускайте тесты на CI с флагом -race.
Пишите тесты с таймаутами, чтобы избежать зависания тестового набора.
Тестируйте не только "счастливый путь", но и сценарии отмены (например, вызов cancel() и проверка, что горутина корректно завершилась).
Изучите и избегайте антипаттернов. Это сэкономит вам часы отладки в будущем.
