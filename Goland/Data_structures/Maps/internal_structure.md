# Внутреннее устройство

Хеширование: основа работы. Хеш позволяет мгновенно определить, в каком бакете искать элемент.

Хеш-функция — это математическое преобразование, которое берёт данные произвольного размера (строку, число, структуру) и превращает их в число фиксированного размера. Это число называется хешом или хеш-кодом.


### Свойства хорошей хеш-функции

- Детерминированность — одинаковый ключ всегда даёт одинаковый хеш. Это фундаментальное требование, без которого невозможно надёжно находить элементы.
- Равномерное распределение — разные ключи равномерно распределяются по всему диапазону хешей. Это минимизирует количество коллизий.
- Быстрое вычисление — хеш должен вычисляться за O(1) или O(n) для строк, где n — длина строки.

```go
// Упрощённое представление внутренней структуры
type hmap struct {
    count     int    // количество элементов в мапе
    flags     uint8  // флаги состояния (итерация, запись и т.д.)
    B         uint8  // log₂ количества бакетов (2^B бакетов)
    noverflow uint16 // примерное количество overflow бакетов
    hash0     uint32 // seed для хеш-функции

    buckets    unsafe.Pointer // указатель на массив бакетов
    oldbuckets unsafe.Pointer // указатель на старые бакеты (при росте)
    nevacuate  uintptr        // счётчик эвакуации
}
```

Бакет (bucket) — это базовая единица хранения данных в мапе. Каждый бакет может хранить до 8 пар ключ-значение. Это не случайное число — оно выбрано как компромисс между использованием памяти и производительностью.

```go
// Упрощённая структура бакета
type bmap struct {
    tophash [8]uint8        // старшие 8 бит хеша для каждого ключа
    keys    [8]keytype      // 8 ключей
    values  [8]valuetype    // 8 значений
    overflow *bmap          // указатель на следующий бакет при переполнении
}
```

> Важно!
> Ключи и значения хранятся отдельными массивами, а не парами. Это экономит память за счёт уменьшения padding.

```log
ЧЕРЕДОВАНИЕ ПАР:
[k1][pad][v1][k2][pad][v2][k3][pad][v3]...
     ↑        ↑        ↑
     Padding после КАЖДОЙ пары = 8 * 4 = 32 байта

РАЗДЕЛЬНОЕ ХРАНЕНИЕ:
[k1][k2][k3][k4][k5][k6][k7][k8][pad][v1][v2][v3][v4][v5][v6][v7][v8]
                                ↑
                                Padding только ОДИН РАЗ = 4 байта
```

Экономия: 28 байт на каждые 8 пар (25% памяти).


### Массив tophash: быстрая фильтрация

Массив tophash хранит старшие 8 бит хеша каждого ключа. Это оптимизация, позволяющая быстро отсеять неподходящие ключи без полного сравнения.

Представьте, что вы ищете книгу в библиотеке. Вместо того чтобы читать название каждой книги на полке, вы сначала смотрите на цвет обложки. Если цвет не тот, сразу переходите к следующей книге. Только когда цвет совпал, читаете полное название.

Вот упрощённая логика поиска элемента в мапе:

```go
// Упрощённая логика поиска элемента
func mapaccess(m *hmap, key keytype) valuetype {
    hash := hashFunc(key, m.hash0)

    // Определяем номер бакета из младших битов хеша
    bucketCount := 1 << m.B           // 2^B бакетов
    bucketIndex := hash % bucketCount // Остаток от деления
    b := getBucket(m.buckets, bucketIndex)

    // Берём старшие 8 бит хеша для быстрого сравнения
    top := uint8(hash >> 56)

    for b != nil {
        for i := 0; i < 8; i++ {
            // Сначала сравниваем tophash (быстро: 1 байт)
            if b.tophash[i] != top {
                continue
            }

            // Только если tophash совпал, сравниваем полный ключ (медленнее)
            if equal(b.keys[i], key) {
                return b.values[i]  // ← Нашли!
            }
        }
        b = b.overflow  // Переходим к следующему overflow-бакету
    }

    return zeroValue  // Ключ не найден
}
```


### Порядок итерации не гарантирован

Из-за того, что элементы распределяются по бакетам на основе хеша, порядок их хранения не связан с порядком добавления. Более того, Go специально рандомизирует порядок итерации, чтобы разработчики не полагались на него.


### Коллизии и их решение

Коллизия возникает, когда два разных ключа получают одинаковый хеш или попадают в один и тот же бакет. Это неизбежная ситуация в любой хеш-таблице.

Go использует метод цепочек (separate chaining) для разрешения коллизий. Когда в бакете заканчивается место (больше 8 элементов), создаётся дополнительный overflow-бакет, который присоединяется к основному.

```
Визуализация цепочек бакетов:

Бакет 0:  [k1, k2, k3, k4, k5, k6, k7, k8] → overflow → [k9, k10, k11, _, _, _, _, _]
          └─ 8 элементов (полный)              └─ 3 элемента

Бакет 1:  [k12, k13, _, _, _, _, _, _]
          └─ 2 элемента

Бакет 2:  [k14, k15, k16, k17, k18, k19, k20, k21] → overflow → [k22, k23, k24, k25, k26, k27, k28, k29] → overflow → [k30, ...]
          └─ 8 элементов (полный)                     └─ 8 элементов (полный)                             └─ ещё overflow

Бакет 3:  [_, _, _, _, _, _, _, _]
          └─ пустой
```

Мапа автоматически увеличивает количество бакетов, когда становится слишком "плотной". Go использует два критерия для принятия решения о росте:

- Критерий 1: Load factor превышает 6.5 (Load factor — это отношение количества элементов к количеству бакетов).
- Критерий 2: Слишком много overflow-бакетов. Если overflow-бакетов больше, чем обычных бакетов, мапа тоже растёт. Это означает, что данные плохо распределены, и нужна реорганизация.


### Процесс эвакуации

Когда мапа решает вырасти:

- Выделяется новый массив бакетов (в 2 раза больше)
- Старый массив сохраняется в поле oldbuckets
- Поле nevacuate устанавливается в 0 (счётчик эвакуированных бакетов)
- Данные переносятся постепенно при каждой операции записи

```
Начальное состояние (B = 2, 4 бакета):
┌────────────────────────────────┐
│ buckets: [B0] [B1] [B2] [B3]   │
│ oldbuckets: nil                │
│ count: 30, loadFactor: 7.5     │ ← Превышен порог!
└────────────────────────────────┘

↓ Начинается рост (B = 3, 8 бакетов)

┌────────────────────────────────────────────────────┐
│ buckets:    [  ] [  ] [  ] [  ] [  ] [  ] [  ] [  ] │ ← Новые пустые бакеты
│ oldbuckets: [B0] [B1] [B2] [B3]                     │ ← Старые данные
│ nevacuate: 0                                        │
└────────────────────────────────────────────────────┘

↓ После первой записи (эвакуировали B0)

┌────────────────────────────────────────────────────┐
│ buckets:    [✓]  [  ] [  ] [  ] [✓]  [  ] [  ] [  ] │ ← B0 распределён
│ oldbuckets: [×]  [B1] [B2] [B3]                     │ ← B0 пуст
│ nevacuate: 1                                        │
└────────────────────────────────────────────────────┘

↓ После второй записи (эвакуировали B1)

┌────────────────────────────────────────────────────┐
│ buckets:    [✓]  [✓]  [  ] [  ] [✓]  [✓]  [  ] [  ] │ ← B0, B1 распределены
│ oldbuckets: [×]  [×]  [B2] [B3]                     │ ← B0, B1 пусты
│ nevacuate: 2                                        │
└────────────────────────────────────────────────────┘

↓ После полной эвакуации

┌────────────────────────────────────────────────────┐
│ buckets:    [✓]  [✓]  [✓]  [✓]  [✓]  [✓]  [✓]  [✓]  │ ← Все данные здесь
│ oldbuckets: nil                                     │ ← Память освобождена
│ nevacuate: 0                                        │
└────────────────────────────────────────────────────┘
```

Рассмотрим конкретный пример выделения памяти:

```
Пример: map[int64]int64 с 1000 элементами

hmap структура:                      48 байт
Бакеты (128 бакетов):                128 * 144 = 18,432 байт
Overflow-бакеты (~5 штук):           5 * 144 = 720 байт
─────────────────────────────────────────────────
Итого:                               ~19 KB
```

Размер бакета зависит от типов ключа и значения. Формула расчёта размера:

```
bucketSize = 8 + 8*sizeof(key) + 8*sizeof(value) + padding

// Примеры:
// map[int]int:        8 + 64 + 64 + padding ≈ 144 байта
// map[string]string:  8 + 128 + 128 + padding ≈ 272 байта
// map[int]struct{}:   8 + 64 + 0 + padding ≈ 80 байт
```


### Указание начальной ёмкости

Если вы заранее знаете примерное количество элементов, всегда указывайте ёмкость при создании. Это избавит от множественных ростов и значительно ускорит работу:

```go
// ❌ Без ёмкости — множество ростов и эвакуаций
m1 := make(map[int]string)
for i := 0; i < 10000; i++ {
    m1[i] = fmt.Sprintf("value_%d", i)
}

// ✅ С ёмкостью — одно выделение, без ростов
m2 := make(map[int]string, 10000)
for i := 0; i < 10000; i++ {
    m2[i] = fmt.Sprintf("value_%d", i)
}
```

Почему это быстрее?

- Без ёмкости мапа растёт многократно: 0 → 8 → 16 → 32 → 64 → 128 → 256 → ...
- Каждый рост требует эвакуации всех данных
- С ёмкостью сразу выделяется нужное количество бакетов
- Никаких промежуточных ростов и эвакуаций

Быстрые ключи:

- Целочисленные типы. int, int64, uint32 — хешируются за O(1), сравниваются за одну операцию
- bool. Всего 2 возможных значения
- Указатели. Фиксированный размер 8 байт, быстрое сравнение адресов

Средние по скорости:

- string. Хеширование O(n) по длине, но оптимизировано в Go
- float64. Требует особой обработки NaN (NaN != NaN)

Медленные ключи:

- Большие структуры. Много байт для хеширования, сравнения и копирования
- Массивы. Аналогично структурам, время зависит от размера


Если вам нужно только проверять наличие элементов, используйте struct{} как значение. Пустая структура не занимает памяти и идеально подходит для реализации множеств (set):

```go
func main() {
    // ❌ Неоптимально: bool занимает 1 байт + padding
    set1 := make(map[string]bool)
    set1["apple"] = true

    // ✅ Оптимально: struct{} занимает 0 байт
    set2 := make(map[string]struct{})
    set2["apple"] = struct{}{}

    fmt.Println("Размер bool:", unsafe.Sizeof(true))       // 1 байт
    fmt.Println("Размер struct{}:", unsafe.Sizeof(struct{}{})) // 0 байт

    // Проверка наличия работает одинаково
    if _, exists := set2["apple"]; exists {
        fmt.Println("apple найден")
    }
}
```


## SwissTable: новая реализация мап в Go

Основные отличия от классической реализации

1. Control bytes вместо tophash. В классической реализации для быстрой фильтрации использовался массив tophash с 8 элементами. SwissTable использует control bytes — специальные байты метаданных, расположенные перед данными.
2. SIMD оптимизации. Главное преимущество SwissTable — использование SIMD инструкций процессора для параллельного сравнения всех control bytes за одну операцию.
3. Группы по 16 элементов. В отличие от классических бакетов по 8 элементов, SwissTable использует группы по 16 элементов. Число 16 выбрано, потому что SIMD инструкции обрабатывают 16 байт за раз.
4. Улучшенная работа с удалениями. SwissTable лучше справляется с множественными удалениями благодаря использованию tombstone-маркеров.


### Производительность

Бенчмарки показывают улучшения в типичных сценариях:

Поиск элементов:

- Простые типы ключей. +30-50% быстрее
- Строковые ключи. +20-40% быстрее
- Большие мапы (>10000 элементов). +40-60% быстрее

Вставка и удаление:

- Примерно на том же уровне или немного быстрее
- Лучше справляется с high load factor

Память:

- Использование памяти осталось примерно на том же уровне
- Лучшая локальность данных благодаря структуре control bytes


### Когда SwissTable даёт максимальный эффект?

Наибольшее ускорение:

- Частый поиск в больших мапах
- Много операций чтения
- Процессоры с хорошей поддержкой SIMD (современные x86-64, ARM)

Меньше эффекта:

- Маленькие мапы (<100 элементов)
- Много операций записи и удалений
- Старые процессоры без SIMD
